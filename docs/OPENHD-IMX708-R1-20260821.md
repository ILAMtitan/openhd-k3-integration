# OpenHD BeagleY-AI IMX708 R1 checkpoint — 2026-08-21

This branch locks the first physically working native OpenHD path for an Arducam B0310 / Sony IMX708 on BeagleY-AI / AM67A (J722S).

It is intentionally a live-upgrade checkpoint layered on the existing R3-qualified OpenHD consumer baseline. The clean installer is left unchanged on this branch so the previously-qualified IMX219 R3 path remains reproducible. Use `apply-imx708-checkpoint.sh` to reproduce this exact checkpoint on an R3 system.

## Matching accelerator checkpoint

This OpenHD branch depends on branch `imx708-r1-20260821` in `ILAMtitan/ti-k3-accelerators`.

The accelerator-side checkpoint records:

- CSI0 Arducam B0310 / IMX708 overlay
- 2304x1296p56 RAW10 graph helper
- GStreamer 1.24 `rggb10le` TIOVX core compatibility rebuild
- default/untuned IMX708 DCC generator
- VISS and Wave5 qualification results

## OpenHD camera type

The new camera type is:

- ID: `151`
- key: `X_CAM_TYPE_TI_J722S_IMX708`
- name: `TI_J722S_IMX708`
- mode: `2304x1296@56`

Existing camera type 150 / IMX219 remains intact.

## Qualified native pipeline

```
v4l2src /run/ti-k3/camera-video, dmabuf-import
  -> video/x-bayer rggb10le 2304x1296p56
  -> capssetter to TI legacy rggb10 metadata
  -> tiovxisp / VPAC VISS
       compatibility sensor slot: SENSOR_SONY_IMX219_RPI
       IMX708 DCC: /opt/imaging/imx708/linear/dcc_viss_2304x1296.bin
       format-msb=9
       AE disabled
       AWB disabled
  -> NV12 2304x1296p56
  -> queue max-size-buffers=1, leaky=downstream
  -> v4l2h264enc / Wave5
  -> H.264 byte-stream, AU aligned
  -> h264parse
  -> rtph264pay mtu=1024
  -> appsink
  -> OpenHD wifibroadcast
```

The TI appsink checkpoint preserves the physically-tested behavior:

```
appsink max-buffers=64 drop=true sync=false name=out_appsink wait-on-eos=false
```

## RF bitrate finding

The first OpenHD run used a 12 Mbit/s Wave5 startup bitrate. With MCS2 and 20 MHz channel width, OpenHD calculated approximately 11 Mbit/s maximum video rate. The TI path does not yet expose dynamic bitrate control to OpenHD, so the encoder stayed at 12 Mbit/s and the delivered video was heavily corrupted.

Setting `h26x_bitrate_kbits=6000` removed the corruption completely on the physical link to the laptop.

R1 therefore locks:

- bitrate: 6000 kbit/s
- GOP: 28
- RTP MTU: 1024

Do not raise the fixed bitrate until Wave5 dynamic bitrate control is implemented and qualified.

## Manual image-quality baseline

TI AE/AWB remain disabled because the deployed TI plugin still uses the IMX219 compatibility sensor slot and contains an IMX219-specific exposure mapping.

For indoor qualification, the selected manual sensor baseline is:

- exposure: 1280
- analogue gain: 512
- digital gain: 256 (unity)

This is applied by `openhd-ti-imx708-prepare` and can be overridden with:

- `OPENHD_IMX708_EXPOSURE`
- `OPENHD_IMX708_ANALOGUE_GAIN`
- `OPENHD_IMX708_DIGITAL_GAIN`
- `OPENHD_IMX708_MODE`

The image is generally correctly colored with the default DCC. A green tint was observed mainly when fluorescent fixtures were directly in frame and highlights were overexposed. This is treated as highlight/exposure/DCC tuning, not a Bayer-order failure. Manual WB offsets are not part of the checkpoint.

## Apply

On an existing R3-qualified system with the matching accelerator checkpoint already installed:

```bash
sudo ./apply-imx708-checkpoint.sh
sudo systemctl start openhd.service
sudo ./verify-imx708-checkpoint.sh
```

The apply script backs up the currently-installed OpenHD binary, camera settings, and systemd drop-in under `/root/openhd-imx708-checkpoint-backups/` before installing the checkpoint.

It leaves OpenHD disabled/stopped after the upgrade so the first launch remains explicit.

## Physical result

The checkpoint achieved all of the following on 2026-08-21:

- OpenHD service started successfully
